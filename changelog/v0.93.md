## v0.93.9 (2026-10-26)

### feat(tools): ask_user 改为无限等待，问题卡新增「关闭」按钮中止任务保留状态

- **内容**：移除 ask_user 的两层 5 分钟超时——工具内部自强制计时器，以及 `definition.timeoutMs` 声明（该声明会让工具总线 `runWithToolLimits` 再设一道看门狗；「工具总线不代为执行」的旧注释已过时）。此后问题**无限等待**用户作答，退出仅两路：会话中止（abortSignal）或关闭问题卡（`ASK_USER_CANCELLED` 哨兵 → abort 错误，不冒充用户回答）。`createAskUserTool` 删除无人使用的 `options.timeoutMs` 参数；工具描述明示无超时。WebUI `QuestionCard` 右上角新增「关闭」按钮（tooltip「中止任务并保留当前状态」），复用现有 abort 链路（`store.abort()` → `POST /sessions/:id/abort` → `abortSession` 顺带 cancel 悬挂问题），会话历史完整保留、可继续开新 run；**有意不提供**「忽略问题继续跑」——需要 ask_user 确认的问题不可被跳过。
- **决策**：大哥拍板：既然是需要用户确认的问题，就不能被时间或忽略跳过（跳过后续不可控）；故超时不是调参而是删旋钮，单一关闭按钮语义 = 中止任务保留状态。

- **已知边界（如实）**：无人值守场景下 ask_user 将永久悬挂直到会话被中止（此前 5min 后自动继续）；自动化调用方需自行处理无人应答。Gateway `askUser` / `resolvePendingQuestion` / `cancelPendingQuestions` 契约未变。

### fix(core): 未知工具错误带 did-you-mean 建议，纠正模型调用不存在工具的自我强化

- **内容**：新增 Layer 0 纯函数 `tool-name-suggestion`（零依赖）；`prepareToolCall` 的未知工具分支改为 `Tool "x" not found. Did you mean "y"?`。判定四档：归一化全等 / 段序颠倒 / 段级后缀（`edit`→`file_edit`）/ 段级前缀（`ask`→`ask_user`）/ 编辑距离 ≤40%；前两档确定唯一目标即短路，其余多候选如实列出（`edit` 同时是 `file_edit` 与 `package_edit` 的尾段，猜死反而会引错），无可靠候选时保持原文案。

- **验证**：新增 `tests/core/tool-name-suggestion.test.ts`（13 用例：简写/重复前缀/拼写错/段序颠倒/归一化全等不带噪声/无关名不给建议）、`tests/harness/constitution-tool-names.test.ts`（6 用例）；`tests/loop-p0-contracts.test.ts` 补 2 条端到端回执断言。相关三套 37 过；loop + context 套件 119 过；core/engine typecheck、eslint、`arch/check-sync.sh` 全绿。
- **已知边界（如实）**：`suggestToolNames` 只纠正「名字」层面的错法，无法判断模型是否本意想调另一个工具；候选集较大且多个候选同分时（如 `read`）只列前两条，排序按同分短名优先，属启发式而非语义匹配。

## v0.93.3 (2026-10-25)

### fix(cli): `getProcessName` 在 macOS 改走 lsof，牢笼内不再静默失效

- **问题**：`getProcessName` 用 `ps -p <pid> -o comm=`，而 macOS 的 `ps` 是 setuid —— Seatbelt 直接拒绝 exec 任何 setuid 二进制（v0.93.2 已归因的 OS 不变量）。结果是**在牢笼内恒返回 null**：`octopi serve start` 的端口占用提示只能给 pid、给不出进程名，且 `getProcessName` / `identifyPortOccupant` 两条测试在沙箱内永远红，每次全量都要人肉判断是否为已知问题。
- **修法**：darwin 上先用 `lsof -p <pid> -a -d txt -Fn`，取首个 `n` 条目。进程的**第一个 `txt` 描述符就是可执行映像**，后续条目是 dyld/mmap 的库（`/usr/lib/dyld` 等），因此取首个而非任一个。`lsof` 非 setuid，牢笼内外均可工作；`ps` 保留为兜底（覆盖 lsof 被裁剪的主机）。Win32 `tasklist`、其他 Unix `ps` 路径不变。
- **语义保持**：macOS `ps -o comm=` 本就返回可执行文件完整路径，lsof 的 `n` 条目语义相同，调用方无需改动。
- **解析独立可测**：抽出纯函数 `firstExecutableFromLsof()`，测试覆盖「取映像不取 dyld」与空输出/无 `n` 行返回 null 两类边界；另加一条 jail 韧性断言（沙箱内自身 pid 必须解析出绝对路径）。
- **降级如实**：跨用户进程（如 root 的 launchd）lsof 无权读取 → 返回 null，与 `ps` 无权限时行为一致，仍属可接受的降级而非假装成功。
- **顺带记录一个未修的同源缺陷**：`getAncestorPidSet()` 仍依赖 `ps -o ppid=`，牢笼内退化为「仅 self + ppid」，使 `killProcess` 的祖先护栏只认一层。lsof 不提供 ppid，macOS 上无干净的非 setuid 替代（`sysctl kern.proc.pid.*` 在现行 macOS 已移除，实测 `unknown oid`），故本次不改，事实留在 `docs/process-isolation{,.zh}.md`。
- **验证**：全量 **3286 过 / 0 败 / 6 跳过**（此前 3280/2，两条恒红转绿）；实机端到端：自身 pid 与同用户他进程（llama-server）均解析出绝对路径，root 进程 `1` 与不存在的 pid 返回 null；`build` / `lint` / `typecheck` 全绿。

### fix(sandbox): exec 被拒时给出可操作归因（EPERM 不再无解释）

- **问题**：jail 内 `execve` 失败只打印 `Operation not permitted`，调用方无法区分两种成因，只能靠试错重发现沙箱不变量。实测代价：查一次进程内存占用用了 3 次无效尝试才绕过。
- **两种成因**（措辞相同、建议相反）：`setuid-exec` —— Seatbelt 拒绝 exec 任何 setuid 二进制，是 OS 不变量（macOS 的 `ps`/`top` 即 setuid，故笼内进程列表必败，**改 profile 也放不开**）；`privilege-deny` —— 生成 profile 显式拒绝**非** setuid 的特权助手（`chroot`/`dscl`，隐式 setuid 规则覆盖不到）。
- **通道**：`isolation.notes` 记事实（牢笼做了什么）+ 新增 `SandboxResult.diagnostics.hints`（下一步怎么办，`shell` 工具以 `hints` 字段透出，与 `file_search` 的 diagnostics 惯例一致）。不污染用户命令的 stderr。
- **不误报**：写盘/网络拒绝措辞相同但**故意不归因**；反向实测写盘拒绝、正常命令、文件不存在均为 `hints=null`；病态 stderr 去重并限 8 个候选，避免无界 `stat`。
- **supervised 回落也归因**：嵌套沙箱下 `sandbox_apply` 失败会走 supervised 路径（agent 自身日常处境），原本只在 `runSeatbelt` 内归因等于失效；改为共用挂载点。此时 `denyExec` 传空——外层牢笼在拒绝而非本项目 profile 生效，不做 deny 清单归因。

### fix(sandbox): 特权 deny 清单改为跨平台超集（不再按单机裁剪）

- **问题**：原清单只覆盖单一拼写，而 SBPL `literal` 是**精确字符串匹配**，不归一化 `bin` vs `sbin` vs `usr/bin`——Debian 的 `su` 在 `/bin/su`、macOS 在 `/usr/bin/su`，漏一个拼写就是一扇门。
- **改法**：按能力分组（su/sudo/sudoedit/pkexec/doas/run0/login/newgrp/chroot/dscl），每组列出各发行版全部拼写；`DEFAULT_PRIVILEGE_DENY_EXEC` 由分组表派生，分组表为唯一真相源。补现代提权面 `pkexec`/`doas`/`run0`/`sudoedit`。
- **决策记录**：**死条目是特性**——指向不存在路径的 deny 行永不匹配、零成本；而缺拼写的代价是安全洞。**不做**按主机探测动态生成：profile 随主机变化会让同一配置在不同机器行为不同，调试成本高于无害噪音。注释与 `docs/process-isolation{,.zh}.md` 均写明「禁止按单机现状裁剪」。
- **测试**：新增 4 例——分组全路径进 profile、关键拼写逐一在场、路径绝对且跨组唯一、宿主覆盖仍整体替换；补上 `arch/open-problems.md:482` 指出的齐套性缺口（原先只断言 `sudo` 一条，挡不住漏拼写）。
- **验证**：全量 3280 过 / 2 败（`getProcessName`、`identifyPortOccupant`，同一沙箱固有限制：笼内 `ps` 不可用，与本提交无关；另有 1 例 `FileWatchSource` 并行负载下防抖抖动，单跑通过）；`build` / `lint` / `typecheck` / `arch/check-sync.sh` 全绿。
