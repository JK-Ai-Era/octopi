## v0.86.35 (2026-10-22)

### refactor(run-guard): 移除判据错位的 token_growth 与无效的 no_progress

收尾 v0.86.32~34 的同类工作：三条规则已从「弱信号」改为「行为特征」，剩下两条经核查各有根因问题，故移除而非修补。

**规则 4 `token_growth` 判据错位**：它用 `tokenGrowthRate > 0.5` 判「上下文膨胀」，但该指标是「最近半窗 token 消耗 ÷ 前一半 − 1」，衡量的是**消耗增速**，不是上下文**绝对大小**。用真实故障 session 日志实测：

| session / turn | 上下文实际变化 | 该指标值 |
|---|---|---|
| `default-web-1792654908416` t1 | 24.5k → 241k（约 10×） | **0.08** |
| `default-web-1792669399277` t2 | 126k → 242k（约 2×） | **0.03** |

涨 10 倍它无感；反而对「单轮读了个大文件」这类正常波动敏感。

更关键的是**它想管的事已有人管**：`run-agent` 的 wrap-up 在每次检查点无条件计算 `contextEstTokens / contextWindowTokens`（默认阈值 0.85），动作是进入收尾模式、让 agent 输出结论——比本规则的 `truncate_context` 更好。后者实现是 `messages.splice(systemEnd, removeCount, 摘要)`，**整段替换历史中部**，直接打穿前缀缓存（B0 红线），且 failureKind `burn` 连续升级后还会 `clear_recent_turns`。

`tokenGrowthRate` 指标本身保留（`run_guard_metrics` 观测可见），只是不再参与裁决；LLM 审查 prompt 中也移除了该行，避免审查者基于错位指标下 `CONCERN/STOP`，同时给失败率补上窗口样本量。

**规则 5 `no_progress` 两个分支都不生效**：
1. `low` 无任何消费方（`checkpoint()` 只取 high/medium）——与 v0.86.31 移除的同名 low 死代码同一个坑。
2. `medium` 要求 `noopStreak >= 3`，而 `run-agent` 在 `consecutiveNoops >= noopThreshold`（默认 3）时已设置 `_noopLoopStop` 并发出可见停止事件（v0.86.32 补的），`shouldStopAfterTurn` 直接结束 turn。本规则只是重复判定，还会多注入一条 hint、污染 `recoveryHistory`。

**结果**：Guard 只保留三类真实异常——同参同结果（无进展循环）、同参同错误（没换方法）、高失败率且无推进（thrash）。上下文压力归 wrap-up / Budget，noop 归 run-agent，职责不再重叠。`RunFailureKind` 中的 `stall` 随之不再被产生（保留在 taxonomy 中）。

**测试**：`tests/run-guard.test.ts` 原「应该检测 token 暴涨」改为「消耗增速不再触发裁决」（断言 `continue` 且 **不返回 `truncate_context`**）；新增「无进展不再单独触发裁决」。**红绿对照**：注入回旧规则后两条用例均失败，恢复后 40 例全绿。

**验证**：`tsc` core/engine/gateway 干净；`tests` 类型门禁 0 新增（148 条存量基线不变）；eslint 干净；全量 `vitest` 3046 passed（3 failed 仍为已知环境限制：沙箱内 `ps` 不可用 ×2、Windows 临时路径用例 ×1；另有一次 `FileWatchSource` 防抖用例在并发下抖动，单独连跑 3 次均通过，与本次改动无关）。

## v0.86.34 (2026-10-22)

### fix(run-guard): 错误循环按「错误是否重复」判，而非「失败了几次」

**问题**：规则 2 用 `consecutiveErrors >= 3`（high / `blowup`）判错误循环。但该计数按**失败次数**算——跑测试 A 红 → 改 → 跑测试 B 红 → 改 → 跑测试 C 红，三次失败、每次错误各不相同，正是红-改-绿调试节奏，却被判 high 并进入 recover；同 kind 连续 3 次后升级 stop。

**判据事实**：`consecutiveErrors` 在 `RunMetricsCollector` 中**只由工具失败递增**（`recordToolResult` 的 `!success` 分支）。core 注释原写「模型错误 + 工具错误」与实现不符，本次一并改正；模型/Provider 错误由 `ProviderPool` 自己的 `consecutiveErrors`（阈值 5）处理，不进 Guard 指标。

**改法**：
- 新增 `CheckpointMetrics.consecutiveIdenticalFailures`：连续「同一错误」次数，指纹 = 工具名 + 参数 + 错误内容（复用 `hashToolCall` / `hashToolOutcome`，错误对象同样剥离 `durationMs` 一类易变字段，否则同一条报错每次都判为不同）。
- 规则 2 主判据改为 `consecutiveIdenticalFailures >= 3` → high/`error_loop`（「同一错误连续 N 次，重试没有换方法」），`>= 2` → medium。语义：**同参同错重复 = 卡住**；连续失败但错误不同 = 探索。
- 保留兜底 `error_streak`：`consecutiveErrors >= 8`（`ERROR_STREAK_SAFETY`）→ high。连续 8 次工具失败且一次未成功，更像工具/环境整体不可用，而非普通调试；3~5 次连续失败远不触发。
- 字段缺失时告警一次，仅走兜底，不退回旧判据（宁可漏报不误杀）。
- LLM 审查 prompt 增加「连续同一错误」一行，让审查者看到诊断信号而非只有失败次数。

**测试**：`tests/run-guard.test.ts` 原「应该检测错误循环」改为「同一错误反复重试」，另补 5 例：3 次/5 次不同错误不得判 error loop、8 次不同错误兜底必须拦、字段缺失不退回旧判据。`tests/run-guard-escalation.e2e.test.ts` 用真实 collector 补 4 例指纹行为：同参同错累加、同参异错不累加、易变字段不影响指纹、成功即清零。**红绿对照**：还原旧判据后 4 条防误杀用例全部失败，而「真 error loop」用例仍绿——证明新判据既止住误杀，也保留了检出能力。

**验证**：`tsc` core/engine/gateway 干净；`tests` 类型门禁 0 新增（148 条存量基线不变）；eslint 干净；全量 `vitest` 3045 passed（3 failed 仍为已知环境限制：沙箱内 `ps` 不可用 ×2、Windows 临时路径用例 ×1）。

**与 v0.86.32 / v0.86.33 的关系**：三条误杀规则同源——判据用了**弱信号**（同名、次数、比例）代替**行为特征**（是否无进展）。现三条分别改为：同参同结果（规则 1）、同参同错误（规则 2）、高失败率且无推进（规则 3）。

## v0.86.33 (2026-10-22)

### fix(run-guard): 失败率规则误杀 —— 「高失败率」不等于「thrash」

**问题**：`high_failure_rate`（规则 3）只看 `toolFailureRate > 0.5` + 存在 ≥3 条轮次摘要。但失败率高本身不是行为异常——编码类 run 里跑测试/编译得红是工作的组成部分（先写失败用例再实现、按错误信息反复调试），失败的调用与成功的编辑交替出现。

**误杀链**（与 v0.86.32 修的 `repeated_tool` 同族，但更隐蔽）：
1. 高失败率 → `medium` / `thrash` → `recover`；
2. 同 `failureKind` 连续 2 次 recover 后，recovery 升级为 `clear_recent_turns: 2`——**把 agent 刚做完的进度从上下文抹掉**，比直接 stop 更难诊断；
3. 连续 3 次 → `stop`。

**关键发现（窗口语义）**：`toolFailureRate` 是最近 10 条工具调用的比例。在这个窗口下，「失败率 > 0.5」与「无连续 2 次失败」不能共存（6F/4S 必然出现连续失败），而连续失败会先触发规则 2（`error_loop`，high）并抢先成为裁决 kind。因此 thrash **真正能独立生效的场景是小样本**：例如 2 次失败 + 1 次成功 = 67%，样本仅 3 条——恰恰是正常调试最常见的节奏。

**改法**（判据收窄为「失败没有换来任何推进」）：
- 新增 `CheckpointMetrics.toolCallsInWindow`（失败率窗口的实际样本量，可选字段），由 `RunMetricsCollector` 填充；缺失时打一次 `console.warn` 且判据不启用（宁可漏报，不退回旧判据误杀）。
- 规则 3 追加两个必要条件：**样本量 ≥ 5**（失败率是比值，2 次全失败也是 100%，不构成证据）与 **`!hasProgress`**（最近三轮无任何成功工具或实质文本，才是真 thrash）。
- 文案改为 `工具失败率 N%（窗口 M 次）且最近无进展`，recovery hint 改为「定位失败根因 / 报告阻塞点」，不再暗示「工具用法不对」。

**测试**：`tests/run-guard.test.ts` 原有「应该检测工具失败率高」改为「高失败率 + 无进展」并为新条件补齐；新增 3 例防误杀（有进展不得 thrash、窗口 2 次全失败不得触发、字段缺失不得退回旧判据）。`tests/run-guard-escalation.e2e.test.ts` 新增真实 collector 驱动的小样本用例（断言 `toolFailureRate > 0.5`、`toolCallsInWindow === 3`、`hasProgress === true` 三个前提成立后仍须 `continue`）与 `toolCallsInWindow` 填充用例。**红绿对照**：还原旧判据后 4 条新用例全部失败，恢复后 31 例全绿。

**验证**：`tsc` core/engine/gateway 干净；`tests` 类型门禁 0 新增（148 条存量基线不变）；eslint 干净；全量 `vitest` 3037 passed（3 failed 仍为已知环境限制：沙箱内 `ps` 不可用 ×2、Windows 临时路径用例 ×1）。

**未做**：规则 2（`consecutiveErrors >= 3` → high/`blowup`）在「连续跑三个都红的测试」时同样会误杀，属同族但判据不同（连续失败 vs 比例），需单独设计「失败是否重复」的指标，本期未动。

## v0.86.32 (2026-10-22)

### fix(run-guard): 长 turn 被静默掐断 —— 同名工具误判为循环 + 停止不可见 + 结束原因无日志

**现象**（`default-web-1792669399277`，2026-10-22）：t2 跑了 99 分钟 / 105 次 LLM 调用 / 155 次工具调用后，工具还在正常返回，突然只剩一条 `<turn_end id="t2"/>` 收口，任务中止；用户确认未做任何输入（无 abort、无错误、预算闸门都没到——`maxWallClockMs=10h`、迭代 105/1000、工具 155/5000、单次调用最长 83s 远低于 watchdog 300s/900s）。

**根因链**：
1. `DefaultRunGuard` 规则 1 用 `consecutiveSameTool >= 5` 判「循环」，而该指标**只数工具名**（`run-metrics-collector.ts`）。编码类 run 天然连续调用 `shell`/`file_edit`（改一行 → 跑 typecheck → 再改），参数每次不同却被判 high/loop → recover；连续 3 次后按升级阶梯 `stop`。这是把正常工作节奏误判为死循环。
2. 停止路径只 `yield { type: 'run_guard_stopped', data: { reason, userMessage } }`，**从不落消息**；`run_guard.stopped` 在 webui 也无消费者。引擎拥有静默终止用户任务的权力，却没有任何可见凭证——比误判本身更严重。
3. run 收口零日志（无 `run_end`、observer trace 未启用），事后只能靠反推落盘消息猜测终止原因。

**改法**：
- **判据**：新增 `CheckpointMetrics.consecutiveIdenticalCalls`（工具名 + 参数 + 结果三者指纹一致，复用 `hashToolCall`/`hashToolOutcome`；指纹前剥掉 `durationMs`/`isolation`/`rawStdoutLength` 等每次必然不同的元数据，否则 `shell` 结果永远不相等、判据对最主要的循环工具失效）。规则 1 改为 `identicalCalls >= 5` → high/`repeated_identical_call`。纯「同名不同参」不再产生规则结果——裁决只消费 high/medium，造一条 low 规则是死代码；需要观测时看 `run_guard_metrics.consecutiveSameTool`。指标生产者未提供新字段时打一次 `console.warn`，不静默空转。
- **指标与开关解耦**：`recordToolResult` 移出 `loopDetection.enabled` 分支——关掉 loopDetection 后 RunGuard 判据曾永远为 0（静默失效）。参数归一为 `?? {}`，与旁路 loop 检测器同口径。
- **可见性（终态才落消息）**：`adaptLoopEvent` 捕获 `stopMessage` / `stopDetail` / `loopEndReason`；runner 收口时若 `agent_end.reason === 'should_stop'`（唯一权威的「提前停止」信号）就落一条 `source='runStopped'` 消息 + `session.metadata.lastStop`。非终态信号不宣称已停止：`security_blocked` 单次拦截后 run 会继续跑完（`terminate: false`），`security_stopped` 文案只描述拦截事实；终态事件（RunGuard / Budget）用**赋值**覆盖而非 `??=`，避免"监督器判定停止：安全策略拦截…"这种串味文案。
- **补上两条静默停止路径**：noop 超限（`_noopLoopStop`）与二次 loop critical（`_loopCriticalTwice`）此前只置标志、不发事件，live UI 完全看不到；现在都写 `state.runGuardStop`，与 RunGuard 走同一 `run_guard_stopped` 事件通道。
- **上下文边界**：`runStopped` 登记为引擎载体（`isEngineCarrierSource`），且 `buildLlmMessages` 显式跳过——它进聊天回放与审计，不回灌 LLM（否则每次停止都在上下文里留痕）。
- **UI**：`ConversationAdapter` 历史回放把 `runStopped` 渲染为 `warning` 系统提示条（不冒充用户气泡，`turnEnd` 仍隐藏）；live 路径新增 `run_guard.stopped` 提示条，`budget.exceeded` 优先使用引擎给出的 `userMessage`。
- **观测**：`finally` 输出 `[timing] stage=run_end dur=… reason=… loopEnd=… stopReason=…`；`adaptState` 提升到 `try` 外层供其读取。
- **`lastStop` 真删**：正常完成时先移除内存字段，持久化后再走 `updateMetadata` 删除——`save` 是 metadata 浅合并，只删内存对象删不掉磁盘键（照 `abortedTurn` 的既有写法）。

**测试**：新增 `tests/harness/run-stop-visibility.test.ts`（15 例）：同名不同参不累加、同参同结果累加、同参不同结果视为有进展、连续 12 次同名不得 recover/stop、相同调用 5 次必 recover、**loopDetection 关闭时指标仍到 Guard（真实走 `runAgentWithReliability`，已做红绿对照：把记录移回开关分支内该用例失败）**、四类停止原因捕获、`should_stop` 才落消息而 `security_blocked` 后 `completed` 不误报、旧形状 `budget_exceeded` 带可读原因、`runStopped` 回放为 warning、`turnEnd` 仍隐藏、载体判定。既有 `run-guard.test.ts` / `run-guard-escalation.e2e.test.ts` 改到新判据，并新增「仅同名不得判为循环」回归。

**已知未覆盖**：runner 的 `runStopped` 落盘门禁 / `lastStop` 写删只有类型与逻辑校验，没有端到端用例（需要完整 SessionAwareRunner 夹具）；`runStopped` 会进入标题生成 prompt 与 session 搜索索引（`title.ts` 只过滤 `metadata.kind`），影响很小，未在本期处理。

## v0.86.25 (2026-10-22)

### fix(delegation): 送达回执 + surfaced 语义 —— dispatch 被丢不再误记已送达

**问题**（v0.86.24 落地时留下的两个议题，大哥拍板收口）：
1. `Delegation.notified` 一名双义：既表示「notify 推送送达」又表示「父经 delegate_get 取回」，且对 LLM 暴露为 `notified` 会让模型误读为「通知没发出去」。
2. 「送达可证伪」只验证到接收端在线：推送 emit 成功后 dispatch 仍可能被丢（`no_agent` / `runtime_stopped`），此时消息从未变成父 session 里的内容，却已记「已送达」且提示消音——结果无声丢失。

**改法**：
- **LLM 面改 `surfaced`**：`delegate_get` / `delegate_list` / `delegate_cancel` 的 summary 输出 `surfaced`（= 结果是否已**送达**：notify 投递或 get 全文取回；list/cancel 只见概览不计）。存储字段 `notified` 不动（零迁移，webui 零消费已核实）。
- **送达回执 + 乐观置位时序**：dropped 事件在 notify 投递的同步微任务链内**先于**投递续体到达，因此 `notify()` 改为**先乐观置位再投递**，投递失败或 dispatch 被丢（`runtime.trigger.dropped`）时由 `markUndelivered` 收回（与失败路径幂等）。最终语义不变：`notified` 只在结果真正送达时为 true。回滚方向安全：宁可提示多亮一次（父 get 消音），不可丢结果。
- **不变量补齐**：「trigger 未送达必有 dropped 事件」——单目标 dispatch 的 skipped 出口（router 命中但目标未注册 / aborted 等）与 fan-out 全丢弃出口此前**不发** dropped 事件，现已对称补发；dropped 事件携带**裁剪** `triggerRef`（`TriggerRef = Omit<Trigger,'payload'>`：id/type/agentId/sessionId/metadata，不含 payload 正文——事件流经 onAll 转发给所有观察者，正文不得随之泄漏）。

**评审**（两轮子 agent 对抗性评审 + 逐条验证）：一轮查出 **P0 时序竞态**（dropped 先于 markNotified 到达导致回滚必然失效，临时探针实证）——初版集成测试手工预置 notified 掩盖了真实时序，已重写为全真链路；二轮复核确认 P0 真实闭合（还原旧时序该用例必红 + 变异实验双向验证），并补钉两处测试质量缺陷（P0 用例加「dropped 确实带本单 delegationId 发生」正向对照；单目标用例改走 router 单目标未注册路径钉住补发分支——原用例走的是零目标旧出口）。已知残余（挂 O5，见 arch/delegation.md §7）：fan-out 混合结果、`RUN_FAILED` 不回滚；回滚与 `delegate_get`/`markUndelivered` 并发时提示可能多亮一次；store 纯内存不落盘；自定义**异步** notifier 投递期间提示会提前消音（默认同步 notifier 无此窗口）；dropped 订阅常驻 events 无 dispose（Gateway 单次合流，重复 createDelegationRuntime 会累积）。

**验证**：`npm run build` / `npm run lint` 干净；全量 `npm test` 2996 tests 绿，3 个既有环境失败与 v0.86.24 相同（干净树可复现，与本次无关）。新增/重写用例：真实 notify 时序 dropped 回滚（P0 回归钉，旧时序必红）、无关 dropped 组合边界（无 delegationId / 不同单 / 未置位）、runtime 丢弃不变量 ×3（runtime_stopped / 单目标 skipped / fan-out 全丢弃，含 triggerRef 防泄漏断言）。delegation / delegation-notify / delegation-tools / agent-runtime-sources 全绿。

## v0.86.24 (2026-10-22)

### fix(delegation): 委派结果自动回传断链修复 —— notify 推送默认接通，未送达不再被误标

**问题**（大哥实测）：子 agent 完成任务后结果**不会自动回传**父 agent，父必须主动 `delegate_get` 才能拿到结果，连"有结果待取"的提示都没有。

**根因**（三层叠加）：
1. 委派默认开启（`arch/delegation.md` §9.2），但 notify 链路的接收端 `AgentSignalSource` 是 opt-in——仅 `agentRuntime.agentSignal: true` 或配置 `escalate.defaultAgentId` 才挂载。配置缺省时（如 `~/.octopi/octopi.json` 无 `agentRuntime` 块），notifier 发出的 `runtime.agent_signal` 在 `gatewayBus` 上**无人监听**，静默蒸发。
2. `DelegateService.notify()` 在投递**前**就无条件 `markNotified()` 且吞掉投递异常——推送死了仍被标成"已送达"，§7.3 `<delegation_status>` 兜底提示也因"已通知"标记一并消失，两个通道全断。且 `bus.emit` 对有无监听者零反馈，「发出」从来就不等于「送达」。
3. Gateway 无条件打 `notify enabled` 日志，掩盖断链。

**改法**：
- **默认接通**（行为变更）：Gateway 委派接线时默认补挂 `AgentSignalSource`。`agentRuntime.agentSignal` 三态：`true`=显式挂载 / `false`=显式关闭 / 缺省=随委派自动补挂（daemon 三态透传，挂载策略收口 Gateway；显式 `false` 现在压过 `escalate.defaultAgentId`）。非委派部署不受影响。接收端挂载失败也降级为 poll + 提示兜底，不崩委派。
- **送达即可证伪**：`createDelegationNotifier` 投递前校验总线上有存活的接收端（`hasAgentSignalReceiver`，`AgentSignalSource` start/stop 引用计数登记），无接收端抛错按投递失败处理——不再把发进空总线的通知算作送达（库嵌入 `buildFromConfig` 路径同样被收口）。
- **送达语义**：`notified` 只在结果真正送达父后置位——notify 投递成功，或父经 `delegate_get` 取回全文（新增 `DelegateService.markSurfaced`）。`delegate_list` 是只读概览**不置位**（结果可能被工具结果截断，宁可提示多留也不误消音）。投递失败保持未送达并**打 warn 留痕**；无投递器时直接不投递、无提示噪音。两种情况都由 `<delegation_status>` 提示兜底。
- **接线防呆**：`ensureAgentSignalSource` 成功后才置挂载标志（失败留重试口），`ensureDelegationRuntime` 首建 promise 合流防并发双建；日志按 push on/off 二分，显式关闭时 warn 说明兜底模式，删除"notify enabled"无条件断言。

**评审**（两轮子 agent 对抗性评审 + 逐条验证后定稿）：一轮查出「notifier 成功≠送达」的根因残留（探针实证）、「挂载标志先置位无回滚」、「list 置位可能误标」、「测试断言弱于声称（TRIGGER_RECEIVED 在路由前就发）」等，均已闭合；二轮复核增量并补齐「`stop()` 实例级计数配平」与「in-flight 占位去重」两处防御（均带回归测试）。`notified` 字段命名（送达 vs 已取回双语义）留作后续议题。

**验证**：`npm run build`（五包 tsc 全过）、`npm run lint` 干净、`arch/check-sync.sh` 通过；delegation / delegation-notify / delegation-tools / agent-runtime-sources / gateway-agent-signal-mount 全绿。**新增 13 用例**：无接收端拒送达、无投递器留提示兜底 + `markSurfaced` 消音、`delegate_get` 取回即送达、`delegate_list` 只读不消音、deadline 迟到竞争 notifier 恰好一次、in-flight 占位拦并发双投、接收端计数配平、`notifyPush:false` 不装 notifier、gateway 三态挂载 ×5（真实 notifier → source → dispatch → 假父 dispatcher 捕获的端到端）；另**修改 3 个旧用例**（其中旧断言"失败也标已送达"是本 bug 的测试侧固化，一并纠正；「投递失败留提示兜底」即其改后语义）。全量 `npm test`：**2991 tests 绿**（3000 总），3 个既有环境失败（`cli-process-utils > getProcessName`、`cli-serve-preflight > identifyPortOccupant`、`harness/temp-path > Windows 临时区`）在干净树全量跑同样复现（前两者进程名探测受沙箱影响、后者 Windows 路径语义用例依赖全量顺序，单跑可绿），与本次无关。

## v0.86.12 (2026-10-21)

### feat(cli): `llm-diff` 输出老化回本判定

**问题**：判断「这次老化划不划得来」此前要手工算——从 dump 里取减掉的字符、燃烧的字符、tokens/char
比率、缓存折扣和调用次数，五步缺一不可。实测中这个判断有反直觉结论（小批次净亏、大批次一轮回本），
手工算极易得出与事实相反的结论。

**成本模型**（`estimateAgingPayback`）：

- 老化 = 一次性付费 + 持续收益：本次调用要把失效尾部按全价重算 → `burned × (1 − discount)`
- 被老化的原文此后每次调用都不再发送，且本按命中价计价 → 每次节省 `saved × discount`
- 因此 `paybackCalls = burned × (1 − discount) / (saved × discount)`；`discount=0.1` 时即 `9 × burned / saved`

**摊薄面用实测值而非估算**：判据是「该次老化之后**实际**发生了多少次调用」，而不是「按 run 分组推算每轮
调用量」。实测发现 `runId` 不等于 turn（一个 turn 会跨多个 run，本 session 有一轮 33 次调用分散在 3 个
runId 上），按 run 分组会把调用量低估到 1，得出「需 19.8 轮」的错误结论。

**输出**（仅在发生历史老化时追加）：

```
history aged into pointers: +38 msg (total 161 → 200), first at msg[374]
payback: saved 25k tok/call vs burned 55k tok → 19.8 calls at 10% cache price — repaid (149 calls followed)
```

未回本时显示差额：`— needs 23.4 calls (≈0.7 runs) more`。

**配置**：新增 `--cache-discount <ratio>`（默认 `0.1`），仅影响回本估算，不影响比对本身；校验区间 (0, 1]
（`0` 会让回本恒为无穷，属误用）。`--limit` 只影响展示，回本判定始终按全量索引计算。

**测试**：新增 5 项（回本公式、未回本判定、零老化 → Infinity、折扣单调性、`--cache-discount` 解析校验），
共 34 项。

（否则会按字符腰斩 JSON 丢定位符）。本次核对该实现时发现两个问题：

**问题 1（真缺陷）**：阶段 2 无条件 `stages.push('content_lines')`。当所有 content 行都短于 200
字符时，阶段 2 实际什么都没改，却仍被记入 `stages`，于是 hint 谎报
`L1 output cap applied (content_lines+preview_cap)`。这会把调用方引向「重跑窄命令拿回完整行」，
而真实情况是预览被省略、应当 `file_read` 具体文件。已改为仅在确有行被截断时记录。

**问题 2（文档缺失）**：预算语义（只约束 matches 清单体，`matchedFiles`/`diagnostics`/`hints`
不计入；超出预算是安全且有意的取舍）此前仅存在于实现细节中。补充注释与
`budgetChars` 字段说明，避免后续把「超出预算」误当 bug 去收紧，从而牺牲定位符。

**测试**：新增 2 项——stage 不谎报（短行场景只应出现 `preview_cap`）、定位符在预算装不下时
仍全保（有意超预算）。合计 10 项。

**已知边界（实测）**：该 session 中 `file_search` 32 条、仅 1 次触发结构化收缩（最长 7726 < 8000）；
`shell` 107 条、1 次触发 L1（8000）；`file_read` 60 条、0 次（阈值 36000）。即 B1 已生效但触发率低，
**当前长上下文的主要来源是条数而非单条大小**。
