## v0.84.4 (2026-10-19)

### fix(engine): manual compaction 400 — summarizer request shape + attribution + failure degradation

**问题**：手动压缩报 `HTTP 400: "messages[0] assistant must provide content, reasoning_content or tool_calls"`。根因是 compact engine 的 `toLlmMessages` 把中段**原始消息序列当对话**转发给摘要模型——只留 role+正文、丢 toolCalls/toolResults/tool_call_id，「只有 tool_calls、正文为空」的 assistant 消息被 provider sanitize 成 `content:null` 且无 tool_calls，严格校验网关直接拒绝。自动压缩不炸是因为其 LLM 摘要走 `LLMSummaryCompressor`（格式化为纯文本单条 user）；手动压缩走 compact engine 的 summarizeFn 路径从未被真实工具轮次数据测过（compact 测试全用纯 user 消息）。非近期重构引入：`toLlmMessages` 自 v0.44.1 出生即如此；`a083ce3`（reasoning/content 分流）移除正文垫底后裸露。

**修正**（`capabilities/compact/engine.ts`）：

- **请求形态**：summarizeFn 路径改为「policy 指令（`buildSystemPrompt`）+ 文本化中段单条 user」，删除 `toLlmMessages`——文本化保留 toolCalls/toolResults 明细，杜绝空 assistant/缺 tool_call_id 形态
- **迭代式合并**：`previousSummary` 随内容进 prompt（`Previous summary: … New content: …`，与 summary executor / LLMSummaryCompressor 同款），LLM 返回即完整更新摘要——删除 `mergeSummaries` 事后拼接（3 处调用点），消除 summaryPort 路径「executor 已在 prompt 合并、引擎又拼接」的双重合并
- **多 agent 归因**（模型 2）：`formatMessagesAsText` / `formatMessagesForSummary`（llm-summarizer.ts 对称）保留 `role(agentId)`（惯例出处 session/history renderMessage）——多 agent 共线的摘要不再张冠李戴；E4 分桶（`(sessionId, agentId)`）与 semanticHistory 过滤不受影响
- **失效降级**：`summarizeFn`/`port.extract` 抛错包 try/catch 转 error 通道（此前直达 HTTP 层，`onSummarizeFail:'truncate'` 对抛错不生效）；空文本化中段不发请求直接降级（空 user/占位内容都过不了严格网关）；全部失败分支保留 `previousSummary`（此前 4 处失败返回仅 1 处保留）
- 契约注释修正：`SummarizeFunction`/`CompactSummarizeFn` 写明「previousSummary 已入 messages、返回即完整摘要」；`summarizePolicy` 生效范围更新

**独立评审**（fresh-eyes 子代理：核心修复确认正确、mergeSummaries 语义删除无 consumer 受损、E4 多 agent 分桶与 round-trip 核验 OK；P1-1 抛错回退缺口 + P2-1/2/3/4/5/7/8 采纳修复；P2-5 引用勘误、P2-8 housekeeping 同 commit）。

**验证**：`compact-summarize-request.test.ts` 7 用例（请求形态/严格网关安全/归因/迭代合并/空文本化降级/抛错降级×2）全绿；compact 相关 20 文件 249 用例全绿零回归；tsc/lint 干净。

## v0.84.3 (2026-10-19)

### feat(engine): decouple the compact working target from the context window (F1-B3)

**问题**（F 节 F1-B3，根因 A1「尺子挂错地方」，方案 `arch/long-session-latency.md` §5 B3）：compact/summary 能力齐全但触发线挂在窗口上——1M 窗口 × 0.6 ≈ 57 万 token，实测 38 万 token 的会话永远摸不到，长会话失忆无兜底；窗口未知的部署则完全跳过 proactive。且触发判据量 raw Message 估算，与 F1-B2 老化后的实际请求不一致——不换尺则 B2 稳态（raw ~40 万）会每 turn 误触发 LLM 摘要（双机制打架）。

**修正**：

- **兜底线挂工作目标**：`contextEngine.targetTokens`（默认 200000，与窗口解耦）× `contextEngine.compactFallbackRatio`（默认 1.5）= 30 万兜底线；再取 **min(目标线, 窗口比例线)**——小窗口（≤ ~45 万，含 example 全部模型）仍走有门槛/冷却的温和 proactive，不被挤成死代码（否则无门槛的溢出路径每 turn 压缩=双机制打架换位置）。`targetTokens: 0` 退回旧窗口比例模式（legacy，逐字节旧行为）
- **触发判据量老化视图**：`applyAgingToMessages` 物化 F1-B2 指针视图后估算（实际请求体量的保守上界）——B2 稳态在兜底线之下（数值锁单测）
- **窗口无关兜底**：target 模式下窗口未知也执行兜底压缩（旧早退路径按 `targetTokens>0` 分流；legacy 保持旧跳过行为）
- **增长门（target 模式）**：再压缩除消息增量外还要求全量口径较上次压缩实质增长（≥25% 阈值）——防持续超线会话每攒 5 条就全量重压（「偶发兜底」变「周期压缩」）。⚠️ 裁决记录：此门最初双模式生效，被既有拍板行为「攒够增量重试/补真摘要」的 3 个回归用例顶回——**legacy 重压节奏是既定契约，增长门只属于 target 新语义**
- `buildStructuralView` 补 tool_call/result 配对对齐（与 applyProactiveCompact 抽共用 `alignViewSplit`）——消除 proactive/结构视图跨轮形状切换时的悬空调用/孤儿结果（严格网关 400 风险）
- `compactFallbackRatio` 引擎侧钳制 ≥1（0 会压成压缩风暴而非禁用）；`proactiveCompactRatio: 0` 确认为两模式共同总开关（注释/文档同步）

**独立评审修订**（fresh-eyes 子代理 6 组 findings 逐条核验：H1/H2 采纳、M1/M2/L1–L4 采纳，其中 H2 按「既有契约不动」收窄为 target 模式专属）：

- [High] H1 缺省对小窗口的死代码化——min 钳制 + 小窗口 proactive 事件回归测试锁死
- [High] H2 持续超线周期重压——增长门（target 模式）+「无实质增长不重压」回归测试；legacy「攒够增量」节奏不变
- [Medium] 契约 5（窗口未知兜底）零覆盖——补 target 模式触发 + legacy 跳过保持两条测试；`context-window-unknown.test.ts` 过时头注释修正
- [Medium] 视图形状跨轮翻转——buildStructuralView 配对对齐（存量 D6 同族一并收口于本路径；MessageSelector 侧仍留 D6）
- [Low] 测量口径「实际请求」措辞过强——文档收敛为「保守上界」；`applyAgingToMessages` 改 role 无关；ratio 钳制；JSDoc/测试注释修正；`compactFallbackRatio` 旋钮补测试

**验证**：`tests/harness/proactive-compact-target.test.ts` 8 用例（防打架数值锁 / 与窗口解耦 / 旋钮 / legacy 退回 / 总开关 / 小窗口存活 / 窗口未知双模式 / 增长门）全绿；proactive-compact × 3 + skill-and-summary-persist + context-compact-events + tool-result-aging 18 + context-window-unknown + context-engine 67 全绿零回归；全量 4 个已知 macOS 基线失败不变；lint/build 干净。配置全链（Zod/接口/bridge/schema/example）+ docs EN/ZH 同 commit。

## v0.84.2 (2026-10-19)

### feat(engine): batch-frozen aging of historical tool results (F1-B2)

**问题**（F 节 F1-B2，方案 `arch/long-session-latency.md` §5 B2 + 缓存纪律 `arch/b0-cache-stable-context.md` §4）：长 session 每轮全额回灌历史工具结果（实测 ~607k 字符 ≈ 请求体量 91%）；B1 只压了源头单条体量，历史跨轮堆积仍线性增长。方案已拍板（40 条原文 / 400 字符指针），但**禁渐进老化**是硬约束——每轮在 recency 边界改写 1 条 = 边界→尾部整段（~65k token）烧前缀缓存（B0 稿 §4）。

**修正**（视图级、零 LLM、write-once、批量冻结）：

- 新模块 `harness/context/tool-result-aging.ts`：`computeToolResultAgingPlan`（完整历史两遍扫描定位真实 user 边界；候选按 `freezeBatch` 成批过冻结线）+ `agedToolResultPointer`（工具名 + 参数要点 + 结果轮廓 + re-run 提示；纯函数定形 + WeakMap 记忆化 = write-once）

- **红线**：当前 run（最近真实 user 以来）永不老化；user/assistant 正文不动；tool_call 参数保留、配对不拆；**error 结果永不降级**（错误可追溯性优先）；不膨胀守卫（仅当指针严格小于原文才降级，小正文不降级）
- 挂钩 `buildLlmMessages`（LLM 视图单点收口）：session 持久层保全量原文（视图级降级）；`estimateLLMMessages` 作用于老化视图——尺子与实际请求一致
- 配置 `contextEngine.historyAging`（enabled / rawWindow / freezeBatch / maxPointerChars，缺省 true/40/20/400）：Zod + 手写接口 + config-bridge + `octopi.schema.json` + `octopi.example.json` 全链同步
- `isEngineCarrierSource` 谓词抽到 `layer-types.ts` 共享（grounding.ts 去重复用）

**独立评审修订**（fresh-eyes 子代理 6 条 findings 逐条核验，5 条采纳——报告是待核验声明，非命令）：

## v0.84.1 (2026-10-19)

### feat(engine): apply locator-preserving L1 output cap to file_search

**问题**（F 节 F1-B1，方案 `arch/long-session-latency.md` §5 B1）：工具结果是长 session 请求体量大头（实测 ≈607k/670k 字符 ≈91%），其中 `file_search` 242,723 字符（58 次）为最大单项、单条实测 72,683 字符——`max_results` 只限条数，单条 match 的 `content`/`before`/`after` 行长**无界**（超长行是单条膨胀元凶）；且 file_search 是内置读工具中唯一没接输出门的（`getBuiltinTools` 不传 summary、registry 无缺省 binding）。

**修正**（机械收缩、零 LLM、定位符零损失）：

- **结构化 L1 收缩** `shrinkMatchesForBudget`（file-search.ts 内）：超预算按序收缩——① 剥 before/after 上下文行 → ② `content` 行截 200 字符（`…[truncated]` 显式机械标记）→ ③ 预览只留前 K 条（其余 `…[preview omitted]` 占位，结构形状保持一致）。**file+line 清单任何阶段全保**；即使定位符清单自身超预算也全保（定位符零损失优先于预算）。不走字符串 gate——截断 JSON 会砍掉尾部定位符
- **结果契约**：`truncated` 语义扩为「有信息被收起」，新增 `truncatedReason: 'max_results' | 'l1_cap' | 'max_results+l1_cap'`（联合类型，与 file_list 的 `truncatedReason` 先例对齐）；`outputCap`（stages/rawLength/budgetChars/contentPreviewChars/previewKept）仅收缩时出现；`hints` 增自纠引导（收窄 glob/path、降 max_results、或 file_read 原文）
- **registry 缺省 binding** `file_search: mode:'never', maxReturnChars: 8000`——L2 永不改写搜索结果（LLM 摘要丢 file:line 保真度）；预算可经 `summary.tools.file_search.maxReturnChars` 覆盖
- **根因修复（独立评审发现）**：`src/cli/daemon.ts` 的 `summary.tools` 转发是点名硬编码（只转 http_request/file_read），而配置 schema 的 `summary.tools.*` 是任意工具名 catchall——file_search/shell/file_list 的配置面全是断头。改为 `resolveSummaryToolBindings` 逐工具名泛化转发（全局 `maxReturnChars` 不混入工具覆盖），对称收口
- **同类盘点**（§5 B1 分档）：定位符/列表类 file_search/file_list/shell → 8k 级低上限 ✓；内容承载类 file_read 36k、git_diff/git_show/project_run 不截（评审材料，历史膨胀交 B2）。git_log/git_status 仍未接线（列表类候选，不在实测 top3，留 B2 后按回归指标定夺）

**验证**：新增 `tests/harness/file-search-l1-cap.test.ts` 8 用例（50k 超长行收缩+定位符完好、context 先剥不动 content、小预算 60 条定位符全保、定位符超预算兜底全保、小结果零扰动、计数/L1 原因区分与组合、registry 缺省 L1-only、daemon 配置路径端到端生效）；builtin-tools 44 过零回归；全量测试 4 个已知 macOS 基线失败不变（getProcessName/端口进程名沙箱固有、`/private/var` 别名、gap-scan 竞态断言）；lint/build 干净；check-sync 3 红 = C6 已知 locator 债。经独立子代理（fresh-eyes）评审后修订：daemon 配置断头根因修复 + 配置路径回归测试、stage 记账只记真实收缩、`truncatedReason` 联合类型、stage-3 注释对齐实现。

- `setSystemPromptAssembler` 契约兼容 shim：`injectedContext` 恢复合并语义（旧自定义 assembler 零能力丢失），新增 `volatileContext`（易变份）；仅 `injectedContext` 时按 E8 缺省整体进快照
- 降级轮（assembler 异常/缺失）保持 E8 形态：锚点进 system、易变份走**新鲜**快照（旧快照不再被 last-only 回放到降级轮）
- 观测面对账：`ContextLayersSnapshot` 双 runtime 条目不再互相覆盖（主行 system 份 + 附加行 snapshot 份），`placement` / `usedSnapshotTokens` 贯通 UI 视图；observer 同步隐藏快照
- abort 用户消息定位排除快照/grounding 插槽；指纹缓存键含 placement（消除双实例键冲突隐患）
- 补直接回归 `tests/harness/runtime-snapshot-replay.test.ts`（last-only 回放 / semanticHistory 排除 / query 净化，4 用例）
- 收益口径校准：工具重轮次的上一轮重灌可达 ~65k token（跨 run 首调用上界 ~6–9s，非典型 ~3–6s），见 `arch/long-session-latency.md` §6
- **根因修复（上线实测暴露）**：runner 视图替换判据 `baseMsgs.length !== session.messages.length`（「长度相等=视图未变」）在「剥旧插槽数 == 本轮插入数」时误判未变、丢弃整张视图——快照/grounding 插槽消失、被过滤的旧插槽复活（实测：快照组已装配 1549 token 却未进请求、01:38 陈旧快照被 last-only 回放）。改为**无条件视图替换**（baseMsgs 即 detach 切片+剥旧+插新的权威视图），回归测试精确复现「剥 1 插 1 计数相等」场景。存量潜伏（grounding/attachment 插槽时代即在，计数偶然抵消才触发），E8 使其高频化
