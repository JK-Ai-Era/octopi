### fix(isolation): bwrap needs an explicit --dev /dev; Seatbelt tests are darwin-only

- **真实 bug（Linux 上 21 个用例失败的主因）**：bwrap 以**完全空的 tmpfs 为根**启动，`--unshare-all` 只创建命名空间、**不提供 `/dev`**（man bwrap 明确：/dev 需 `--dev DEST` 或 `--dev-bind` 显式要求）。原 argv 绑定了 `/usr /bin /lib /etc` 却没有 `/dev`，于是任何打开 `/dev/null` 的程序都报 `could not open '/dev/null' for reading and writing`——git 首当其冲，导致 `git_status` / `git_status_snapshot` / undo EOL / dedicated-tools 全链路失败。**同一原因连带 `path-denylist-coverage` 的 git 用例**（其 fixture 直接跑 `git init/commit`）。
  - 修法：argv 增加 `--dev /dev`（挂载新 devtmpfs，非宿主 bind，不引入逃逸面）。
  - 同时修正一句错误注释（原写 "bwrap supplies its own /dev"，是它误导了实现）。
- **测试错在平台假设，不是代码**：`explainSeatbeltExecDenial` 只在 darwin 被生产路径调用（`withExecDiagnostics` 首行即 `if (process.platform !== 'darwin') return pending`），但测试无守卫地在 Linux 上跑它，并断言 macOS 布局 `/usr/sbin/chroot`；Ubuntu 上 chroot 在 `/usr/bin/chroot`，绝对路径 stat 不到 → 解析返回 null → `kind` 为 `undefined`。修法：该 describe 加 `describe.skipIf(process.platform !== 'darwin')`，语义上更准确（这段逻辑与 bwrap 无关）。
- **验证**：macOS 全量 5771 用例通过、Seatbelt 6 个用例在 darwin 上仍正常运行（未误跳过）；Linux 侧以 CI 为准。

### fix(ci): build before test, drop bogus webui install, actions v5

- **首次运行全红的三个真实原因**（都是配置与实际不符，而非测试本身退化）：
  1. **test job 缺 build**：测试内有 `@octopi-agent/engine/harness` 等裸导入，经 `package.json#exports` 解析到 `packages/engine/dist/`；`tests/gateway-agent-signal-mount.test.ts` 等还会 fork 子进程，其入口 `run-serve-child.js` 同样在 dist 内。全新 checkout 无 dist → 实测 52 个文件 / 136 个用例失败（CI 为 58/157，平台差异下少数用例不同）。
  2. **`npm install --prefix packages/webui` 是错的**：`packages/webui` 属 workspace 成员（`workspaces: ["packages/*"]`），root `npm ci` 已把依赖装到根 `node_modules`，实测 `tsc -p packages/webui --noEmit` 直接通过。反而 `--prefix` 脱离 workspace 上下文去 registry 查内部包版本，而仓库版本长期领先于已发布版本（0.125.1 vs registry 0.122.0），触发 `ETARGET`。
  3. `actions/checkout@v4`、`actions/setup-node@v4` 内部仍是 node20 运行时，被强制在 node24 上跑并产生弃用警告 → 升 `@v5`。

- **端到端验证**（本机模拟完整链路 `clean → npm ci → build → 删 dist → artifact → npm test`）：564 文件 / 5771 用例全绿；`generate:schema` 零 diff。Linux runner 上的最终结果以 CI 自身为准。

### ci: add GitHub Actions workflow (test · lint · schema-sync)

- **为什么**：README 声称 `550+ test files`、AGENTS.md 要求「改 Zod 就重新生成 `octopi.schema.json`」，但两者此前**没有任何自动检查**——测试是否仍绿只有作者自己知道，schema 分叉完全靠人记得。对一个要对外发布的引擎，这两件事都应当可被外人验证，而不是靠信任。
- **三个 job 与各自防止的退化**：`test`（全量 5747 测试）；`lint`（eslint + tests 类型基线 + webui tsc）；`build-and-schema`（构建完整性 + `generate:schema` 后 `git diff --exit-code octopi.schema.json`）。
- **顺序约束（实测得出，非推测）**：`scripts/generate-octopi-schema.mjs` 读取的是编译产物 `dist/config-schema/index.js`，而 `dist/` 被 `.gitignore` 排除、CI 全新 checkout 中不存在——已验证缺失时以 `ERR_MODULE_NOT_FOUND` 失败。故 schema 检查只能放在 build 之后，不能并入 test job。
- **检查非空转已验证**：注入一个 Zod 字段并重新构建后，该步骤正确产生 3 行 schema diff 并失败；恢复后零 diff。
- **刻意不做**：覆盖率门禁（覆盖率是描述不是质量，设门禁会诱导写无意义测试）、多平台矩阵（Windows 沙箱尚未实现，只会制造噪声）、真实 API e2e（`env` 中显式置空 `OPENAI_API_KEY`，防止将来误加 secret 使测试转为依赖外部服务）。
- **同步**：README / README.zh.md 首屏加入 CI 徽章；`Status & boundaries` 增补可操作门槛（Node ≥ 24 的 `node:sqlite` 理由、v1 单进程限制），让读者在安装前而非安装后才知道。

### feat(skills): 双层技能架构——公共技能层 + per-agent 覆盖层（C 方案）

- **架构**（大哥拍板）：Skill 发现从「per-agent 拷贝」改为**双层**——公共技能层 `OCTOPI_HOME/skills/`（随包种子、一份全共享）+ per-agent 覆盖层 `agents/<id>/skills/`（role preset 技能、用户定制），**同名 skill 由 agent 层赢**。动机：通用技能 N 份拷贝 → 1 份（升级一处生效，drift 面从 N 收敛到 1），同时给 agent 私有技能留正式位置。「同名覆盖」是双层并存的合并规则，不是动机本身。
- **实现**：`paths.sharedSkillsDir`（布局派生单一来源，与 sessions/knowledge 同规，不开新配置旋钮）；`DefaultSkillManager.discover` 接受目录数组按序合并（后层同 id 覆盖），`load()` 按 per-skill sourceOf 回源（覆盖后读到的必须是覆盖层文件），`SkillDefinition.layer` 标注来源层；builder/wire-agent-builder/config-bridge/run-assembly/gateway 五处接线（共享层先扫、agent 层赢）；`probeAgentHomeHealth` 双层计数（同名去重）；init 内置种子改灌公共层（copy-if-missing 语义不变），agent 覆盖层不再落内置拷贝。
